# Prowl

Decades of Northwestern undergraduate research: [SURG](https://undergradresearch.northwestern.edu/funding/surg/) grants (2007–2024), [Expo](https://undergradresearch.northwestern.edu/share/expo/) projects (2003–2026), and honors theses (1980–2026). Search by topic, method, field, or person.

## Raw data

Every source is saved as fetched under `data/raw/<source>/`, which Git LFS stores, and the pipeline reads only those files, never the sites they came from: live pages, Wayback Machine captures and Common Crawl records can all disappear. The scripts that download them (`backend/pipeline/fetch_*.py` and `scrape_*.py`) skip every file already saved, pin the captures they use, and save the Wayback listings they pick captures from, so rerunning one without `--refresh` makes no request. Most sources have a `manifest.jsonl` giving each file's original URL, capture timestamp and SHA-256 (see `backend/pipeline/download.py`).

Each source's parser writes what it reads to `data/records/<source>.jsonl` (SURG grants, Expo and Symposium posters, theses and NURJ papers), all in one shape: one record per piece of work, with its people, abstract, full text where the source has it, and where to check it. The stages after parsing read only these files. `backend/pipeline/records.py` describes the shape.

Clones skip `data/raw/` (see `.lfsconfig`); fetch a source with `git lfs pull -I "data/raw/<source>/**" -X ""`.

Material that is not public stays out of this repository, in private repositories also stored in Git LFS:

- [`mmss-papers`](https://github.com/ishanjmukherjee/mmss-papers): the MMSS thesis library, behind a Northwestern login, read by `backend/pipeline/parse_mmss_theses.py` from a checkout at `mmss-papers-wt/mmss-papers` beside `grantsearch-wt`.
- [`expo2020-videos`](https://github.com/ishanjmukherjee/expo2020-videos): the Expo 2020 presentations' YouTube videos, posted unlisted by the students.
- [`expo2022-videos`](https://github.com/ishanjmukherjee/expo2022-videos): the voiceovers of the 2022 Expo's ForagerOne posters, also unlisted, downloaded by `backend/pipeline/fetch_forager_videos.py` into a checkout at `expo2022-videos-wt/expo2022-videos`.

## Query log

The site logs every search with the results it returned, every project page loaded, and each click, opened abstract and share of a result, to one Postgres table (`events`, in the Railway project's Postgres service). `backend/querylog.py` describes each field and writes the rows; the frontend sends the reports and the headers that tie a tab's requests together (`report` and `visitHeaders` in `frontend/src/App.tsx`).

- A visit is one browser tab: a random id in the tab's `sessionStorage`, gone when it closes. No IP address, cookie or User-Agent is stored. Railway keeps its own request logs, which do hold addresses and URLs, for as long as its plan retains them.
- Nothing is deleted from the log. Queries often name people, so it stays in the database: don't commit an export. A query that goes into `data/eval/` should be read first.
- Results update as a visitor types, so most logged searches are of a query half typed; the last before a pause, a click or the visit's end is the one they settled on. `shown` says which results were really on screen.
- Open `/?internal=1` once in each browser you build or test the site in (`/?internal=0` undoes it), and its events are marked `internal`. Requests from scripts have no visit id.
- The app logs only when `DATABASE_URL` is set, which on Railway refers to the Postgres service's. The database has no public address, so it is read from inside the project.
- To read the log, from a checkout linked to the Railway project: `railway ssh --service web python -m querylog export --days 7` prints it as JSON lines, and `railway connect Postgres` opens `psql` on it. Both go over SSH, so the machine's key must be registered with Railway first (`railway ssh keys add`).

## Roadmap

- [x] Exact search with single or double quotes around a phrase.
- [x] Stop expanding acronyms that an abstract coins for itself, or that mean something else to most people who type them.
  - A card's `acronyms` say what one project means by its letters, and search used to expand them in every query. expo-2022-087 writes "antibiotic resistance (AR)", so "ar" became antibiotic resistance; one card's SEC made "sec filings" a search for the Super Elongation Complex, and one card's MARS made "mars rover" one for Multivariate Adaptive Regression Splines. A vote between cards could not catch this, since most keys rest on a single card.
  - Now the cards only propose. Each key is judged once for the whole site, by reading what the cards propose for it beside how the site's titles and abstracts write the same letters, under the brief in `prompts/acronym.md`. `data/generated/acronyms.jsonl` holds the verdicts and is all that search reads (`backend/pipeline/acronyms.py`).
  - Of the 1,953 keys the cards propose, 1,483 are expanded and 470 are left as typed. Against the 1,202 keys expanded before: 286 no longer are (AMP, CART, CCD, DNS, FEES, MARS, MIA, PIC, SEC), and 568 newly are. Most of those are keys no title or abstract writes (ACA, FEMA, NAFTA, IVF), where a card gives the acronym for words its project spells out or takes it from a thesis's full text; the old rule expanded only keys that titles and abstracts write in capitals. "cdms", which the cards write only inside "SuperCDMS", is added in `data/overrides.jsonl`.
  - Keys of up to three characters were judged twice and are expanded only where both readings expand them. The two readings split on 84 of the 855, nearly always over a rival meaning one reader weighed more, so a few acronyms with a clear leading meaning stay as typed (RBC, CSF, API, BMI).
  - After a new source is carded, `uv run python -m pipeline.acronyms` lists the keys to judge: those without a verdict, and those for which a card now proposes a meaning the verdict was not judged against. Until they are judged they are not expanded. The same command checks the queries in `data/eval/acronyms.jsonl`, which must gain an expansion or stay as typed.
  - Not done: a query word matches a key only as a whole word, so "ipscs" and "iPSC-derived" are not expanded though "ipsc" is.
- [ ] Mark the matched words and phrases in results for every query, not only quoted phrases. The guiding principle is that results should explain themselves.
  - Today `Marked` in `frontend/src/App.tsx` highlights only quoted phrases.
  - First, mark BM25 matches: the query words (by stem) wherever they appear in the title, people, advisors and abstract. This is cheap.
  - Also mark lexical matches of query expansions: when an acronym in the query is expanded ("qpcr" to "qPCR, quantitative polymerase chain reaction"), mark the expansion where it appears, since today only the dense side sees it and an abstract that spells it out would otherwise show no mark.
  - Name matches matter most. When `people.People.pins` puts a person's projects first, mark the name that matched, so a visitor sees why a project they didn't search for by topic came first, and which of several people with that name it is.
  - Reach goal, likely worth doing: dense matches often share no words with the query, so also mark the abstract sentence closest to the query, shaded more lightly than exact matches. Embed abstract sentences offline and score them against the query vector already computed.
  - Further reach, worth considering: explain matches that came from a card. "Spectral geometry" finds the SURG grant "Can one hear the shape of a clarinet?" only through its card's concepts and generated queries, and the card shows just the title, year and author, so there is nothing to mark. A quiet line such as "Matched on: spectral geometry (inferred from the title)", with the gloss in a tooltip, would name the card term that actually caused the match (the winning generated query in the dense score, or the card fields BM25 hit).
    - Show it only when card terms were decisive and the match is strong, never styled as data, so cards still never pass for real data.
    - It would also make bad cards visible, to be fixed in `data/overrides.jsonl`.
- [ ] Filter results by a set of disciplines (multi-select).
- [ ] Filter results by event and year, as two filters that combine: events (SURG, Expo, and each source added later, such as the Symposium, NURJ and the theses) and years (a range or a set). A project matches if any of its events falls in the chosen years, so "Expo, 2024" keeps a 2023 SURG grant presented at Expo 2024.
  - Make the "SURG 20xx" and "Expo 20xx" tags on each result (`frontend/src/App.tsx`) clickable: clicking one sets the event and year filters to that tag. The tags should then look clickable without crowding the result.
  - This matters more with each source added, as results mix more kinds of work across more years.
- [ ] Autocomplete in the search box.
  - Suggest completions as a visitor types: people's names (from `backend/people.py`), project titles, disciplines and common topic terms.
  - Results already update as you type, so suggestions should help finish a query, not replace the live results.

- [ ] Bake in some recency bias.
  - Once the older sources above are indexed (Expo 2012-2019, SURG 2010-2019, NURJ from 2003, Economics theses from 2001), research goes back decades, and today ranking ignores dates entirely, so a 2004 paper and a 2025 project of equal relevance rank the same.
  - The usual approach is a decay function of age folded into the relevance score, as in Elasticsearch's [`function_score`](https://www.elastic.co/guide/en/elasticsearch/reference/current/query-dsl-function-score-query.html) decays (gauss, exp or linear, tuned by `scale`, `offset` and `decay`). Adding a constant 1 to the decay makes it a multiplier between 1 and 2, so old but strong matches are nudged down rather than buried. Here that would multiply the RRF `fused` score in `backend/search.py`, with age taken from a project's latest year.
  - Web engines apply freshness per query ("query deserves freshness"): strongly for news-like queries, barely for evergreen ones. Google Scholar keeps relevance as the default and offers a separate recent-first mode that it says ranks recent papers "the way researchers do" rather than sorting by date alone. The year filter already covers explicit intent, so a mild default bias may be enough.
